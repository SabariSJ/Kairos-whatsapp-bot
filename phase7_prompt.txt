## 4. Student Authentication and Video Eligibility

The existing Common Backend and PostgreSQL database must remain the authority for payment and enrolment status.

Before granting video access, verify:

1. Student registration exists.
2. Registered phone number and country code match.
3. Payment status is `Paid`.
4. Enrolment status is `Active`.
5. Student's assigned course language is valid.
6. Requested video belongs to the student's assigned course.

### Access control rules

| Student status | Video access |
|---|---|
| Registered, payment Pending | Denied |
| Payment Contacted | Denied |
| Payment Confirmed but not Paid | Denied |
| Payment Paid, enrolment not Active | Denied |
| Payment Paid and enrolment Active | Allowed |
| Unknown student | Denied |
| Cancelled payment/enrolment | Denied |

Never trust payment status, phone number, language or course ID supplied only by the frontend.

The Common Backend must verify eligibility whenever a new playback session is created.

The student must not be able to bypass these checks by changing a URL or API parameter.

## 8. Download, Sharing and Forwarding Restrictions

The player interface must not provide:

- Download button.
- Share button.
- Forward video button.
- Copy video URL button.
- Public video links.
- Direct S3 object links.
- External sharing actions.
- Picture-in-picture playback, where supported and controllable.
- Unnecessary external casting options, where controllable.

Additional requirements:

1. Use a custom player interface if necessary.
2. Disable native download controls where supported.
3. Do not expose permanent video URLs.
4. Use short-lived playback authorisation.
5. Prevent unauthorised playback session reuse.
6. Implement appropriate session expiry.
7. Consider concurrent-session restrictions.
8. Consider a student-specific visible watermark if technically feasible.

The watermark should use a registration ID or masked identifier and timestamp. Do not expose unnecessary personal information.

**Important security limitation:** Hiding download/share controls does not guarantee that video copying is impossible. Screen recording, screenshots and external cameras cannot be completely prevented by a web player.

Use existing DRM where available, private S3 storage, secure sessions and backend authorisation together.

Do not claim absolute prevention of copying.

Do not weaken existing DRM protection to make player controls work.

## 10. WhatsApp Bot Integration – Complete Student Flow

Preserve the existing WhatsApp Bot and its existing production functionality.

The bot calls the Common Backend.

- Student registration.
- Payment status.

- Assigned course.
- Assigned language.

**Step 4 – Eligibility decision**

If the student has Paid status and Active enrolment, allow video access.

**Step 5 – Course display**

Show the assigned course:

- English: Business Success Class.
- French: Cours de Réussite Commerciale.

**Step 6 – Video selection**

Display the six available videos in the assigned language.

**Step 7 – Secure player access**

When the student selects a video, the bot provides a secure classroom/player access link.

**Step 8 – Player session verification**

The Common Backend validates the student's session and video authorisation.

**Step 9 – Video streaming**

The existing streaming/DRM system securely delivers the selected video from the private AWS S3 bucket to the existing media player.

**Step 10 – Student watches the video**

The student watches using the improved existing player with:

- Play/Pause.
- Rewind 10 seconds.
- Forward 10 seconds.
- Progress bar.
- Playback speed.
- Volume.
- Fullscreen.
- Resume playback.
- Previous/Next video.

### Ineligible student messages

- Not enrolled: Active enrolment is required.
